# Tags on NVRs and cameras

## Summary

NVRs and cameras carry free-form `{ type, value }` labels (e.g. `location: HQ`). The UI shows them as capsules and
edits them in the Edit NVR dialog; `GET /api/v1/cameras` returns them and can filter by them, so a client can group
or select cameras by location without its own mapping table.

## Model

```ts
interface Tag { type: string; value: string }
```

One table, keyed by the NVR id or camera id (no foreign key — the id can point at either table):

```sql
CREATE TABLE IF NOT EXISTS tags (
  id TEXT NOT NULL, type TEXT NOT NULL, value TEXT NOT NULL,
  PRIMARY KEY (id, type, value)
);
```

- An entity can hold several values of one type; duplicates collapse.
- Deleting an NVR deletes its tags and its cameras' tags in the same transaction.
- Existing databases pick the table up on the next start (`CREATE TABLE IF NOT EXISTS`); nothing to migrate.

## API

| route | |
|---|---|
| `GET /api/nvrs`, `GET /api/nvrs/:id`, `GET /api/v1/cameras` | every NVR and camera has `tags: Tag[]` (`[]` when untagged) |
| `GET /api/tags` | every tag as `{ id, type, value }` (UI autocomplete) |
| `PUT /api/tags/:id` | replace all tags on one NVR or camera; 404 for an unknown id |

### Filtering `GET /api/v1/cameras`

`?filter=<json>`:

```json
{ "nvrs": { "tags": { "location": ["HQ", "Lab"] } }, "cameras": { "tags": { "zone": ["gate"] } } }
```

- Within a type, any listed value matches (OR); every listed type must match (AND).
- `nvrs` keeps matching NVRs with all their cameras. `cameras` keeps matching cameras and drops NVRs left with none.
- No filter or `{}` returns everything, as before.
- Invalid JSON, a wrong shape, unknown keys or an empty value list → 400 naming the field.
- The typed client takes `filter` as an object and JSON-encodes object query values.

## UI

- Capsule pill: type muted, value emphasized.
- Grid: NVR tags beside the NVR name; camera tags on the camera tile.
- Edit NVR dialog: a Tags field for the NVR and a Tags column per camera. `+` opens an inline `type: value` input with
  suggestions from existing tags; Enter adds, Esc cancels, `×` removes. Saved with the rest of the dialog.

## Rejected

- Tags inside `PUT /api/nvrs/:id`: that route requires the whole connection config, which makes scripted tagging
  awkward. A dedicated `PUT /api/tags/:id` serves both the dialog and scripts.
- A dedicated `location` column or table: the user asked for plain `{type, value}` so new kinds of labels need no
  schema change.
